# Simulator and benchmark choice for verified subgoal RL

Prepared 2026-10-22; coordinator update 2026-10-23. This is a conditional recommendation, not a selected simulator or completed experiment. Scope: simulation-only manipulation, unfamiliar scenes, image/text subgoals, learned progress rewards that can decrease after setbacks, and independent completion verification. User confirms a Linux computer with an NVIDIA 5070; its variant, VRAM and software environment have not been inspected. Cloud compute is an option, not a purchase made.

## Recommendation

**Start with ManiSkill if a supported Linux/NVIDIA training machine is available.** Its existing RL baselines, parallel simulation/rendering, heterogeneous scenes, and task-building API fit the proposed experiments. Begin with one existing manipulation task and a small custom perturbation set; do not build a new simulator. This recommendation is an inference from documented capabilities, not a measured speed or research-quality comparison. [ManiSkill repository](https://github.com/mani-skill/ManiSkill)

**If the immediate constraint is a Mac without a suitable remote GPU, start the learning journey in robosuite.** Its installation guide explicitly supports macOS/Linux and operation with or without a GPU. Develop reset/step/reward/evaluation code locally, then measure whether visual RL needs remote compute. ManiSkill also lists macOS CPU simulation and rendering, but its installation page contains contradictory prose about macOS support; this needs a pinned-version smoke test. [robosuite installation](https://github.com/ARISE-Initiative/robosuite/blob/master/docs/installation.md), [ManiSkill installation](https://maniskill.readthedocs.io/en/latest/user_guide/getting_started/installation.html)

**Closest-work exception:** Robometer's Appendix E.1 uses SAC with DINO image features on two LIBERO-90 tasks. If reproducing that result becomes our first paper experiment, start and remain on its compatible LIBERO stack rather than porting it to ManiSkill and losing a controlled comparison. ManiSkill remains the preferred general RL learning/pilot option. Choose one primary stack after the feasibility check; do not maintain two by default. [Robometer protocol](https://arxiv.org/html/2603.02115v2#A5.SS1).

Keep **Stonefish as a later underwater study**. Starting with underwater rendering, hydrodynamics, custom task construction, RL infrastructure, and a new verifier simultaneously would confound the learning and research questions. A simulator-to-simulator extension still does not demonstrate real-world transfer.

## Experiment and comparability boundaries

These are proposed design constraints, not claims about published benchmark rules:

- Keep an **unchanged standard-task track**: published task definitions, initialization/evaluation states, observation/action spaces, horizon, success predicate, and disclosed training data/interactions. Record exact package versions and commits. Match the specific reference paper's protocol before comparing its numbers.
- Put new objects, occluders, changed lighting/layouts, failure injections, or revised terminal predicates in a **separate custom track**. Reusing a simulator or task name does not make those results standard-benchmark SOTA.
- Define “unfamiliar” explicitly: held-out object identity, scene layout, appearance, or task composition. A fresh reset seed alone does not demonstrate all of these. Split by the chosen factor before collecting reward/verifier data.
- Keep simulator truth separate from policy-visible observations. Oracle state can provide training labels and evaluation truth, but any privileged policy inputs require a labeled comparison. Evaluate the learned verifier against the oracle; never use its own prediction as proof it is correct.
- Test the actual completion semantics: e.g. object placed and released, remains stable after a waiting interval, or drawer stays closed. If added semantics alter the original success predicate, report both the standard and added criteria.
- Learn nonmonotonic progress from successful and failed/reversed transitions, including drops, slips, wrong-target placement, and reopened drawers. Distinguish estimated progress, RL reward, and the stop decision. A score increasing with elapsed time is not evidence of physical progress. Check whether repeated undo/redo actions can exploit the learned reward.
- Compare fixed subgoals, oracle subgoals, learned subgoals, and no subgoals while holding controller capacity and interaction budget fixed. Include sparse task reward and a documented hand-designed dense reward before attributing gains to the learned reward.

## Feasibility spike before a large training run

Budget proposal: at most two focused workdays, with a compute-time/cost cap chosen before remote jobs. No installation or training was performed for this memo.

1. **Reproduce the environment:** inventory the Linux GPU using `nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv`; record OS, Python, torch build, CUDA runtime and simulator versions. Verify the selected PyTorch/runtime supports the actual GPU architecture, then test both rendering and GPU simulation. Older LIBERO install pins are historical protocol evidence, not instructions to install an old CUDA build blindly on a 5070. Run one task, reset/step loop, state observations and RGB, saved episode, explicit seed/config/version. Confirm action ranges, control rate, termination versus truncation, and success labels.
2. **Establish executable control:** run a provided baseline/checkpoint if available; then a short reference RL run with the native reward. Require repeatable successful episodes before debugging a learned reward. A failure here is an infrastructure/control issue, not evidence against subgoals.
3. **Measure the real workload:** compare state-only and intended RGB resolutions at several environment counts; record steps/second, peak VRAM/RAM, reset failures, and rollout latency. Include learned-model inference. Extrapolate the proposed three-seed pilot's wall time from measurements, not README peak FPS.
4. **Audit labels:** construct success, near-success, setback, and deceptive-view cases. Save synchronized visible observations and separate oracle labels. Confirm the evaluator detects undoing a subgoal and distinguishes temporary contact from stable completion.
5. **Verify the interface:** pass a fixed text subgoal and an image target through the proposed controller/reward interface. Image targets should not accidentally reveal hidden evaluation scenes or unavailable camera views. Use fixed subgoals before adding a generative planner.
6. **Go/no-go:** proceed only if the environment/controller works, labels are auditable, at least one intended held-out split is constructible, and measured runtime fits the agreed budget. Otherwise simplify observations/task scope, use demonstrations to initialize the controller, or switch to the local robosuite path. Do not add a second simulator merely to rescue an untrained controller.
